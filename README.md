# preaudit

A pre-audit pipeline for Foundry projects. It runs the build, the test suite, coverage, static analysis, symbolic execution and mutation testing, normalizes every tool's output into one findings list, and writes a single report.

It is a tool for a human reviewer, not a replacement for one: every finding in the report is raw tool output until someone has verified it.

## Usage

```bash
npm install
python -m venv .venv && .venv/Scripts/pip install slither-analyzer   # .venv/bin/pip on Linux/macOS

npm run preaudit -- run <path-to-foundry-project>
npm run preaudit -- run <path> --harness <dir>          # add engagement-specific tests (e.g. Halmos properties)
npm run preaudit -- run <path> --only build,slither     # subset of stages
```

| Option | Meaning |
|---|---|
| `--out <dir>` | run folder (default `reports/<project>-<timestamp>`) |
| `--harness <dir>` | extra tests layered onto a copy of the project; put them under `test/preaudit/` (see below) |
| `--only <stages>` | any of `build,tests,coverage,slither,fuzz,medusa,halmos,mutation` |
| `--mutate <files>` | files to mutate (default: non-interface files in `src/`) |
| `--mutants <n>` | max mutants per file (default 40) |
| `--solc <version>` | solc version for mutation testing (default: read from the pragma) |
| `--fuzz-runs <n>` | runs per fuzz test in the fuzz stage (default 5000) |
| `--invariant-runs <n>`, `--invariant-depth <n>` | invariant campaign size (default 256 runs × 100 calls) |
| `--medusa-seconds <n>` | Medusa campaign length (default 300) |

The target is never modified: every run works on a copy in `<run folder>/workspace`, with the harness layered on top.

Harness tests live under `test/preaudit/`. They are written to break the contract, so they are kept out of the project's own suite (the tests, coverage and mutation-score stages) and only run in the property stages: fuzz properties (`testFuzz_*`) and invariants (`invariant_*`) in the fuzz stage, `check_*` properties in the Halmos stage.

Output:

- `report.md`: pipeline summary and findings grouped by severity
- `findings.json`: the same findings, machine-readable
- `slither.json`, `mutation.jsonl`, `gambit_results_*.json`: raw tool output
- `logs/<stage>.log`: each stage's console output

Requirements: Node 20+, Foundry, Python 3.10+ and Docker. Halmos, Gambit and Medusa run in a Linux container (`docker/Dockerfile`, built automatically on first use) because neither installs on native Windows. Slither is taken from the repo's `.venv` if present, otherwise from `PATH` (override with `SLITHER_BIN`).

## Stages

| Stage | Tool | Where it runs |
|---|---|---|
| build | `forge build` | host |
| tests | `forge test --json` | host |
| coverage | `forge coverage` (src only) | host |
| static analysis | Slither | host |
| fuzz / invariants | `forge test` at 5000 fuzz runs and 256×100 invariant calls; every failure comes with a counterexample | host |
| stateful fuzzing | Medusa, on a suite with a `medusa.json` (e.g. one generated by Pashov's fizz skill) | Docker |
| symbolic execution | Halmos, on the contracts that define `check_*` properties | Docker |
| mutation testing | Gambit + the project's own tests | Docker |
| AI review | [Pashov Audit Group skills](https://github.com/pashov/skills) (x-ray, solidity-auditor, fizz), vendored in `vendor/pashov-skills` | see below |
| triage + report draft | LLM, then human verification | planned |

### Pashov skills

`vendor/pashov-skills` pins [pashov/skills](https://github.com/pashov/skills) (MIT) as a git submodule: `git submodule update --init`. They are interactive Claude Code skills (x-ray: threat model and invariants; solidity-auditor: multi-agent AI audit; fizz: Echidna/Medusa suite generation). The pipeline does not launch them on its own: an unattended agent with a shell, reading untrusted client code, needs a deliberate decision about sandboxing and permissions first. A fizz-generated suite is picked up by the medusa stage.

## Benchmark: Cyfrin PuppyRaffle

[Cyfrin/4-puppy-raffle-audit](https://github.com/Cyfrin/4-puppy-raffle-audit) is a practice codebase with known bugs. The harness in `benchmarks/puppy-raffle/test/preaudit/` holds one symbolic property, four fuzz properties and one invariant, each stating a rule the raffle should keep. The full pipeline runs in about 90 seconds:

```
npm run preaudit -- run ../audit-targets/puppy-raffle --harness benchmarks/puppy-raffle
```

| Stage | Result |
|---|---|
| tests | 18 passed, 0 failed (the project's own suite) |
| coverage | lines 84%, branches 69% |
| Slither | 22 findings |
| fuzz | 4 fuzz + 1 invariant properties, all 5 broken, each with a reproduction |
| Halmos | 1 property violated (fee overflow) |
| mutation | score 68%: 13 of 40 mutants survive the project's tests |

How the known issues were found:

| Known issue | Found by |
|---|---|
| Reentrancy in `refund` (drains the contract) | Slither, rated only **medium**; the fuzz property proves it: the attacker leaves with 4 ETH for a 1 ETH ticket |
| Weak randomness in `selectWinner` | Slither (`weak-prng`) |
| Strict balance equality in `withdrawFees` (griefable via `selfdestruct`) | Slither (`incorrect-equality`) |
| `totalFees` overflow (uint64, Solidity 0.7.6 has no checked math) | Halmos: `entranceFee = 2^95` |
| Unsafe `uint256` → `uint64` cast of the fee | Halmos, same counterexample |
| Unbounded duplicate check in `enterRaffle` (DoS) | fuzz: 323 players cost 51M gas, over a 30M block |
| `getActivePlayerIndex` returns 0 for both "not found" and the first player | fuzz: any outsider address |
| Winner contract without `receive`/`fallback` blocks the raffle | fuzz: `selectWinner` reverts when the players are contracts that reject ETH/NFTs |
| `selectWinner` counts refunded seats, so recorded fees exceed the balance | invariant: enter, enter, refund, draw → 1.2 ETH of fees recorded against 0.2 ETH held |

All nine, with the caveat that matters for selling this: the harness properties were written by someone who knew what to look for. On a real engagement the properties come from reading the code and the protocol's intent, which is the part of the work tools don't do.

Surviving mutants worth a look: deleting `require(playerAddress != address(0))` in `refund` (the double-refund guard), deleting `totalFees = 0` and `require(success)` in `withdrawFees`, and deleting the assignment in `changeFeeAddress` all leave every test passing. So the parts of the contract that move money are barely tested, which is exactly where the reentrancy bug lives.

Slither also flags `arbitrary-send-eth` on `withdrawFees`, which looks like a false positive: the recipient is the owner-set fee address.

## Pitfalls this pipeline handles

- **Foundry 1.x vs Halmos.** Foundry's "dynamic test linking" rewrites `new Contract(...)` in tests into `vm.deployCode(...)`, which Halmos doesn't support, so every property that deploys a contract errors out. The Halmos stage builds with `FOUNDRY_DYNAMIC_TEST_LINKING=false`.
- **Pre-0.8 `assert` hides violations from Halmos.** Before Solidity 0.8, a failing `assert` compiles to the INVALID opcode, which Halmos doesn't count as a failure, so a violated property reports PASS. Harnesses for old codebases revert with `Panic(1)` instead (see `benchmarks/puppy-raffle`), and the stage raises a warning whenever a path hits INVALID.
- **Windows line endings.** Gambit writes LF mutants; against a CRLF checkout every diff would span the whole file. The mutation script normalizes the (disposable) copy first.
- **Halmos and invariant tests.** Halmos also runs `invariant_*` tests symbolically, which doesn't terminate on a real handler. The stage only points Halmos at contracts that define `check_*` properties.
- **Invariant counterexamples on first discovery.** On the run that first breaks an invariant, `forge test --json` reports the counterexample as `null` and only saves the call sequence to its cache. The fuzz stage replays failed invariants once to recover the sequence.
- **Old forge-std assertion messages.** DSTest-style asserts (forge-std from 2023 and earlier) report their message in `decoded_logs`, which `forge test --json` only fills at `-vv`.
